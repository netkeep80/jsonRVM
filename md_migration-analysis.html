Анализ перехода jsonRVM на Go, Rust или WebAssembly

Статус: Анализ Версия: 1.0 Дата: 2026-02-26 Связанные issue: #11 Контекст: Подготовка к реализации jhub (jhub-tz.md)

1. Текущее состояние проекта

1.1 Обзор jsonRVM (C++17)

jsonRVM — виртуальная машина для исполнения программ на языке «Модель Отношений» (RM), представленных в формате JSON. Реализована на C++17, версия 3.0.0.

Ключевые характеристики:

  • ~2500 строк кода (заголовочные файлы)
  • 60+ базовых операций
  • Встроенная поддержка параллелизма (std::execution::par)
  • Расширение через динамические библиотеки (DLL)
  • Зависимости: nlohmann/json, doctest, cpp-httplib, xml2json

1.2 Критические проблемы текущей реализации

Проблема Серьёзность Влияние на jhub
Загрузка DLL только на Windows (windows.h) Критическая jhub требует Linux/macOS/Windows
Кодировка CP1251 вместо UTF-8 Высокая API и JSON требуют UTF-8
Нет CI/CD для тестирования Высокая jhub CI/CD требует стабильности
Windows-специфичный синтаксис (for each) Средняя Не компилируется на Linux/macOS
Жёсткое ограничение контекстов (4 уровня) Средняя Ограничивает гибкость jhub pipeline
Отсутствие JIT/кэширования Средняя NFR-1: чтение репо < 100 мс
Нет REST API Средняя jhub FR-2.5, FR-3.3 требуют API

2. Требования jhub к jsonRVM

Согласно спецификации jhub-tz.md, jsonRVM используется как:

  1. Движок исполнения CI/CD (FR-3.1): JSON-пайплайны исполняются через jsonRVM
  2. Верификатор требований (FR-2.2): JSON-требования проверяются через jsonRVM
  3. Web GUI движок (FR-5.1): Web GUI — JSON-приложение на jsonRVM
  4. Ядро jdb (Фаза 5): Исполняемые JSON-документы в базе данных

Нефункциональные требования jhub, влияющие на выбор языка:

  • NFR-5 Кросс-платформенность: Linux, macOS, Windows — все три
  • NFR-1 Производительность: Открытие репо ≤ 100 мс для 10 000 коммитов
  • NFR-2 Масштабируемость: До 100 узлов Docker Swarm
  • NFR-3 Надёжность: RPO ≤ 1 секунда (WAL)

3.3 WebAssembly (WASM)

Важное уточнение: WebAssembly — это не язык программирования, а целевой формат/платформа для компиляции. jsonRVM может быть скомпилирован в WASM из C++, Go или Rust. Поэтому анализ разделён:

3.3.1 WASM как дополнительный таргет для C++ (Emscripten)

Аспект Описание Важность
Плюс: Минимальные изменения кода Emscripten компилирует C++ в WASM Небольшие затраты
Плюс: Запуск в браузере FR-5.1: Web GUI на jsonRVM Самодостаточность
Минус: Нет DLL плагинов Динамическая загрузка невозможна в WASM Потеря расширяемости
Минус: Нет прямого FS Виртуальная файловая система, Emscripten FS Сложность jdb
Минус: Нет нативных threads без COOP SharedArrayBuffer требует заголовков COOP/COEP CI runner ограничен
Минус: Размер бинарника C++ WASM обычно > 5 МБ Медленная загрузка GUI
Минус: Нет серверного использования WASM в браузере, не для серверного CI runner jhub backend

3.3.2 WASM + WASI (серверная сторона)

Аспект Описание Важность для jhub
Потенциал WASI позволяет запускать WASM вне браузера FR-3.3 CI Runner
Изоляция WASM sandbox для безопасного выполнения CI шагов FR-6 Безопасность
Портируемость Один WASM файл — любая WASI runtime NFR-5 Кросс-платформенность
Зрелость WASI preview 2 (2024) — ещё не полностью готов Риск нестабильности
Производительность 10–30% медленнее нативного кода NFR-1 latency
Экосистема wasmtime, wasmer — растущие, но не production-ready Риск

3.3.3 Оценка WASM как самостоятельного подхода

Кросс-платформенность: ★★★★★ (абсолютная — "write once, run anywhere")
REST API: ★★★☆☆ (через WASI, ограничено)
Производительность: ★★★☆☆ (10-30% медленнее нативного)
Docker-интеграция: ★★★☆☆ (wasmtime в Docker, нестандартно)
WebAssembly: ★★★★★ (это и есть WASM)
Сложность миграции: ★★★★☆ (проще для браузерного использования)
Экосистема JSON: ★★★☆☆ (зависит от языка-источника)
Итог: ★★★☆☆ (3.0/5 — перспективно, но незрело для production)

5. Рекомендация

5.1 Основная рекомендация: Go + WASM (TinyGo) для Web GUI

Рекомендуется переход на Go как основной язык реализации jsonRVM в контексте jhub.

Обоснование:

  1. jhub — платформа разработки, а не HPC система. Приоритеты: надёжность, скорость разработки, кросс-платформенность — не максимальная производительность CPU. Go удовлетворяет всем требованиям jhub.
  2. Открытый вопрос в jhub-tz.md (Раздел 7): "Какой язык для API Server?" — Go является очевидным ответом:
    • Kubernetes, Docker, Terraform написаны на Go
    • Go — стандарт Cloud Native экосистемы
    • jhub использует Docker Swarm → логично писать на том же языке
  3. NFR-1 (100 мс открытие репо): Go + оптимизированный JSON парсинг (gjson/jsoniter) легко достигает этого при 10 000 коммитов.
  4. FR-5.1 (Web GUI на jsonRVM): TinyGo компилирует Go в < 200 КБ WASM, что делает Web GUI реалистичным.
  5. Постепенная миграция: Архитектура jsonRVM (заголовочные файлы ~2500 строк) позволяет написать Go реализацию параллельно, сохранив C++ версию как reference implementation.

5.2 Альтернативная рекомендация: Rust для Production Critical компонентов

Rust рекомендуется если в jhub будут требования к:

  • Безопасности на системном уровне (выполнение недоверенного JSON кода)
  • Extreme performance (обработка тысяч CI pipeline одновременно)
  • WASM для CI Runner (WASI + wasmtime: изоляция выполнения)

Rust также позволяет использовать unsafe блоки для постепенной миграции с C++ кода.

5.3 WebAssembly — не замена, а дополнение

WASM не является заменой языка для серверного jsonRVM. Рекомендуется использовать WASM для:

  • Браузерного Web GUI (FR-5.1) — jsonRVM в WASM выполняет JSON программы прямо в браузере
  • CI Runner изоляция (WASI) — безопасное выполнение недоверенных pipeline

6. Стратегия миграции

Вариант A: Полный переход на Go (Рекомендуется)

Фаза 1 (1-2 месяца): Портирование ядра jsonRVM на Go
- Реализация интерпретатора RM на Go
- nlohmann/json → encoding/json или gjson
- Тесты: портирование doctest сценариев на testing/go
Фаза 2 (1 месяц): Кросс-платформенность и DLL
- Plugin system через Go plugin package
- CI/CD для Linux/macOS/Windows
Фаза 3 (2 месяца): jhub интеграция
- REST API (net/http + chi)
- Docker интеграция (docker SDK for Go)
- TinyGo WASM для Web GUI

Вариант B: Постепенная миграция C++ → Rust

Фаза 1 (2-3 месяца): Параллельная Rust реализация
- serde_json как JSON backend
- Постепенный перенос модулей
Фаза 2 (2 месяца): WASM + WASI
- wasm-bindgen для браузерного GUI
- wasmtime для CI Runner изоляции
Фаза 3 (2 месяца): jhub интеграция
- Axum REST API
- tokio для async CI runner

Вариант C: Кросс-компиляция существующего C++ (Минимальные затраты)

Шаг 1: Устранить Windows-специфичный код (for each → for)
Шаг 2: dlopen/LoadLibrary абстракция (1 неделя)
Шаг 3: Emscripten для WASM браузера (Web GUI)
Шаг 4: Добавить HTTP REST API (cpp-httplib уже есть)
Шаг 5: Docker образы для Linux/macOS

Вариант C — наименьший риск и наименьшие затраты, но не решает фундаментальные проблемы архитектуры для jhub.

8. Заключение

Для реализации jhub рекомендуется следующая стратегия:

  1. Краткосрочно (Фаза 4-5 jhub): Исправить критические проблемы C++ версии:
    • Кросс-платформенная DLL загрузка (dlopen + LoadLibrary)
    • Удаление Windows-специфичного синтаксиса
    • UTF-8 вместо CP1251
    • Добавить Linux CI/CD
  2. Среднесрочно (Фаза 6 jhub): Начать реализацию jsonRVM на Go:
    • Go лучше всего соответствует требованиям jhub как платформы
    • Поддерживать C++ реализацию как reference implementation
    • Использовать Go WASM (TinyGo) для Web GUI
  3. Долгосрочно: Рассмотреть отдельные компоненты на Rust для:
    • CI Runner изоляция (WASI sandbox)
    • Критические пути производительности

WebAssembly — не отдельный вариант языка, а целевой формат развёртывания. Рекомендуется использовать WASM для браузерного Web GUI (через Go/TinyGo или Rust/wasm-pack), но не как основной серверный runtime для jhub.
